# 34일차: 계정·게스트 이전·적립식 투자 검증

## 검증 환경과 재실행

- 운영 데이터에 접근하지 않도록 `demo-portfolio-day34` Firebase Auth·Firestore 에뮬레이터를 사용했다. 실제 Firebase 계정·토스 키·Google OAuth 자격 증명은 사용하지 않았다.
- Node.js 22와 Java 21을 준비한 뒤 `npm ci`, `npm run test:day34`를 실행한다. `firebase.json`의 Auth 9099·Firestore 8080 포트를 사용한다. CI의 `firestore-rules` 작업에서도 같은 테스트를 실행한다.
- 시세·거래일은 고정 가짜 응답을 사용한다. 소급 반영 기준일은 `2026-10-08`로 고정해 테스트가 실행 날짜에 따라 달라지지 않게 했다.

## 적용한 수정

- 적립식 거래 문서 ID를 규칙 ID와 **원래 예정일**로 고정했다. 같은 규칙을 두 화면에서 동시에 실행하거나 실패 후 다시 실행해도 동일 예정일은 같은 문서에 기록된다.
- 기존 매수 여부도 실제 체결일 대신 `scheduledDate`로 확인한다. 예전 이력에 예정일이 없으면 거래일을 사용한다. 여러 예정일이 같은 휴장 후 거래일로 이동해도 각각의 매수를 유지한다.
- 36일차에 포트폴리오 원장 버전과 Firestore 트랜잭션을 추가했다. 동시 갱신으로 버전이 달라지면 최신 원장을 다시 읽어 서로 다른 거래를 병합하고, 같은 거래를 동시에 수정한 경우에는 자동 덮어쓰기 대신 재시도 안내 오류를 반환한다.

## 검증 범위의 한계

- Google 계정은 Auth 에뮬레이터에서 가상 ID 토큰으로 로그인했다. 현재 화면의 `signInWithPopup` 및 실제 Google 제공자 설정·허용 도메인은 검증하지 않았다. 이는 검증 환경에서 확인한다.
- 종가·환율·거래소 휴장 정보는 실제 외부 API가 아니라 고정 응답이다. 토스 연동과 API 권한·허용 IP는 39~40일차에 확인한다.
- 36일차에 동시 수동 매수, 서로 다른 자동매수 규칙, 거래 삭제와 새 매수의 동시 실행을 추가해 총 10개 에뮬레이터 시나리오를 확인했다. 여러 기기에서 같은 거래를 동시에 편집하는 경우에는 충돌 오류를 반환하도록 하며, 실제 운영 트래픽과 대용량 원장은 검증 환경에서 다시 확인한다.
